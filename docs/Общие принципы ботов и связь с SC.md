# Общие принципы 15 реализованных ботов и связь с SC-каталогом

Анализ 15 реальных production-ботов (Telegram/VK-ассистентов на LLM), сделанных за последние полгода на одном и том же скопированном каркасе: `alekseev`, `cicero_bot`, `cognitive_interview`, `corruption`, `dialogic_argumentative_bot`, `dialogic_supportive_bot`, `gb_analytical_bot` (разобран ранее отдельно), `gb_edu_bot`, `gb_philosophy`, `hanskelsen_bot`, `lawyer_bot`, `legalmentor_bot`, `raymers`, `reflector`, `reflector_kolb`, `strategic_transcripts`, `tamozhennik`. (4 папки — `biology_sas`, `dialogic_agent`, `forum_letters`, `gb_philosophy_bot` — пустые, `gb_philosophy 2` — дубликат `gb_philosophy`, оба исключены из анализа.)

Цель документа: зафиксировать, что реально повторяется в коде между ботами (не в теории, а по факту — с точными путями к файлам и цитатами), и связать каждый повторяющийся паттерн с SC-каталогом из Портфеля 42 — тем же способом, что и в файле [«Словарь соответствий SC-ТЗ.md»](Словарь%20соответствий%20SC-ТЗ.md) (читайте его первым для общего словаря понятий).

## Часть 1. Общие архитектурные принципы (по фактическому коду)

### 1.1. Единая файловая структура каркаса

Во всех 15 ботах один и тот же набор файлов, почти всегда с идентичными именами: `bot.py`/`vk_bot.py` (интерфейс+роутинг), `skills.py` (промпты-навыки), `rag.py` (ChromaDB-обёртка), `settings.py` (env-конфиг), `usage_tracker.py`, `model_loading.py`. Непрофильный код (RAG-слой, usage tracking, LLM-клиенты) совпадает между копиями на 70–90%, включая идентичные магические числа, комментарии и даже баги.

Прямое доказательство копипаста без очистки — «протекшие» следы прежних версий:
- В `hanskelsen_bot/logs/usage_log.json` встречается запись с `"context": "STEVE_SYNTHESIS"` — интент, которого нет ни в одном текущем навыке этого бота.
- В `corruption/logs/usage_log.json` — контексты `ANALYZING_STAKEHOLDERS`, `CASE_DISCUSSION`, не совпадающие с текущими 7 навыками.
- В `dialogic_supportive_bot/logs/usage_log.json` — контекст `EXPLANATION`, отсутствующий в нынешнем `skills.py` (бот эволюционировал из более раннего «объясняющего» прототипа).
- `reflector/README.md` описывает несуществующий `app/rag.py` — README не обновлялся после того, как RAG выпилили.
- `gb_edu_bot/README.md` дословно называется «Hans Kelsen Bot» — README скопирован из `hanskelsen_bot` по ошибке.

### 1.2. Роутинг: один LLM-классификатор интентов + плоский if/elif

Практически универсальный паттерн (13 из 15 ботов): одна async-функция `intent_recognition(llm, query)` классифицирует свободный текст в фиксированный набор строковых категорий по few-shot промпту с явными «ПРИЗНАКАМИ» для каждой категории, возвращает строго `{"response": "CATEGORY"}`. Диспетчер — плоский `if/elif` в `bot.py`/`vk_bot.py`, назначающий async-функцию-воркфлоу. Везде есть терминальная ветка `IRRELEVANT`.

Количество категорий варьируется от 2 (`alekseev`: `LEGAL_QUESTION`/`IRRELEVANT`; `strategic_transcripts`: `EXPLANATION`/`IRRELEVANT`) до 8 (`raymers`). Везде есть явная инструкция про поведение при неуверенности («если не уверен — выбирай X»).

**Исключения — два бота без LLM-классификации, с явной state machine вместо неё:**
- `cognitive_interview` — enum `BotState` с 10 линейными блоками (B1→B10), переход только при `layer_complete=true` и явном подтверждении пользователя.
- `reflector` и `reflector_kolb` — идентичная механика: enum `BotState`, метод `_route()`, переход управляется флагом `layer_complete`, который каждый скилл возвращает в JSON.

**Промежуточный случай** — `cicero_bot` (`corruption`): LLM-классификация есть, но дополнена «мягким якорем» — `last_skill_anchor: dict[chat_id -> {skill, question}]`, передаваемым в промпт классификатора, чтобы отличать продолжение текущего навыка от переключения.

### 1.3. Единый JSON-контракт ответа модели

Без исключений во всех 15 ботах каждый промпт требует строго `{"response": "..."}` (иногда с дополнительными полями — `errors`, `progress_detected`, `has_thesis` и т.п.), инструкция «КРАЙНЕ ВАЖНО... БЕЗ markdown» дублируется в начале и в конце промпта. Везде есть защитный парсинг с фолбэками: сначала прямой `json.loads`, затем regex-поиск `{...}`, затем возврат сырого текста как `response`.

### 1.4. In-memory ChatMemory — везде, без исключений

Идентичный класс `ChatMemory`/`ChatHistory` в каждом боте: `dict[chat_id -> List[Tuple[role, text]]]`, усечение до последних N сообщений (N варьируется от 2 до 40 — не вынесено в конфиг, «магическое число» копируется вручную), форматирование в текст `"User: ...\nAssistant: ..."` для вставки в промпт. Везде без персистентности — состояние полностью теряется при рестарте процесса.

### 1.5. RAG на ChromaDB + bge-m3 — единый стек

Без исключений: `chromadb.PersistentClient` + LangChain, embeddings `BAAI/bge-m3` (либо локально через `HuggingFaceEmbeddings`, либо через удалённый `InfinityEmbeddings`-сервер по `EMB_MODEL_URL` — выбор варьируется даже между Telegram- и VK-версией одного бота). Ingestion — `pdfplumber` + `RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)`, метаданные `source`+`page`+`chunk_index`, автоиндексация при пустой коллекции на старте.

Поиск почти везде — чистый semantic similarity (`similarity_search_with_relevance_scores`), без BM25/гибрида. **Единственное исключение — `gb_edu_bot`**: гибридный поиск BM25 (rank_bm25) + semantic через Reciprocal Rank Fusion (RRF, k=60), плюс леммализация фамилий авторов через pymorphy3 для keyword-boost — это самая развитая RAG-реализация из всех 15.

Общие архитектурные классы `SingleVectorStore`/`MultiVectorStore` со стратегиями `"chunks"` (обычные top-k фрагменты) и `"full_case"` (реконструкция полного документа из всех чанков одного `source`) встречаются в 10+ ботах — паттерн явно родился в одном боте (по следам кода — вероятно, `alekseev`, судя по наиболее «базовой» реализации) и разошёлся копированием, местами не до конца задействованный (например, в `strategic_transcripts` и `dialogic_supportive_bot` `MultiVectorStore` реализован, но используется только один `SingleVectorStore`).

**Уникальные вариации поверх общего RAG-стека:**
- `hanskelsen_bot`: `KSRFVectorStore` — двухступенчатый поиск по решениям КС РФ (anchor-документ → fetch всех chunk по `decision_number`), плюс третий уровень источников — веб-поиск через Perplexity API (302.ai).
- `cicero_bot`/`corruption`: query rewriting — отдельный LLM-вызов переформулирует разговорный запрос в юридическую терминологию перед поиском (`transform_query_to_legal_terms`), причём навык `opponent` делает двусторонний поиск (отдельные запросы для истца и ответчика).
- `strategic_transcripts`: neighbor-expansion — после top-k хитов достаются соседние чанки того же документа (`chunk_index ± window`) и склеиваются в один блок «до/после».
- `legalmentor_bot`: `random_cases()` — для генерации нового учебного кейса берётся не top-k по релевантности, а случайная выборка документов.
- `tamozhennik`: часть базы знаний (список ТСТК) живёт не в Chroma, а в плоском CSV с точным match — гибрид векторного и табличного поиска.

### 1.6. usage_tracker.py — общий, но неравномерно распространённый модуль

Присутствует в 11 из 15 ботов, почти дословно совпадает: подсчёт токенов через `tiktoken` (с fallback-энкодером для неизвестных моделей), захардкоженный прайс-лист в рублях (GPT/Claude/Gemini/embeddings — притом что реально используемые модели — Coze/302.ai, которых часто нет в прайс-листе, из-за чего `cost_rubles` тихо становится `0.0`), поля `timestamp/user_id/model/context/input_tokens/output_tokens/cost_rubles/input_text/output_text`.

Видна явная эволюция формата хранения между копиями:
- **Ранняя версия** (`gb_philosophy`, `dialogic_supportive_bot`): весь лог — один JSON-массив, при каждой записи файл целиком читается и перезаписывается (read-modify-write) — не потокобезопасно, деградирует с ростом лога.
- **Поздняя версия** (`gb_edu_bot`, `hanskelsen_bot`, `cicero_bot`, `tamozhennik`, `strategic_transcripts`): JSONL append-only — построчная дозапись без перечитывания всего файла.

**Отсутствует полностью в 4 ботах:**
- `cognitive_interview` — заменён на персистентный SQLite (`db.py`, `aiosqlite`), логирующий структуру сессии/диалога, а не токены/стоимость.
- `reflector`, `reflector_kolb` — то же самое: SQLite (`sessions`+`turns`) вместо usage_tracker; README упоминает `usage_tracker`/`tiktoken`, но фактического кода нет (артефакт недописанного шаблона).
- `legalmentor_bot` — тоже заменён на SQLite (`debate_sessions`, `feedback_results`, `consultant_logs`), с собственным CLI-инструментом просмотра логов (`python db.py user <id>`).

### 1.7. model_loading.py — двухпровайдерный LLM-слой

Без исключений: два взаимозаменяемых клиента с единым интерфейсом `.ainvoke(prompt) -> str`:
- **`CozeLLM`** — через `cozepy.AsyncCoze`, поллинг статуса чата (`ChatStatus.IN_PROGRESS`) раз в секунду.
- **`A302LLM`** — 302.ai, submit-then-poll (`async=true` → `task_id` → `GET /async_result`), таймаут 300 секунд, `aiohttp.TCPConnector(limit=100, limit_per_host=50)`.

Выбор через `LLM_PROVIDER` env-переменную. Везде есть устойчивый защитный парсинг ответа (`extract_response_text`/`_extract_text` с многоуровневыми regex-фолбэками) — прямое следствие того, что structured JSON output не гарантирован ни одним из двух провайдеров.

### 1.8. Явный, систематический запрет «давать готовый ответ / выносить вердикт / оценивать»

Это центральный, повторяющийся в каждом без исключения боте (кроме чисто справочных — см. ниже) дидактический паттерн, выраженный почти взаимозаменяемыми формулировками:

- `gb_analytical_bot`: «не формулирует тезис за студента, не пишет структуру текста, не оценивает в баллах»
- `cicero_bot`/`corruption`: «НИКОГДА не говори «задал верное направление», «интересная мысль» — это уклонение от оценки»
- `hanskelsen_bot`: «НЕ используй оценочные формулировки: «хорошо», «плохо», «молодец», «неправильно». НЕ ставь баллы или оценки»
- `dialogic_argumentative_bot`: «Do NOT help the student clarify, polish, or strengthen their position»
- `dialogic_supportive_bot`: «Do not use empty validation phrases ("Great point!", "You're absolutely right!")»
- `reflector`/`reflector_kolb`: «Только описательный режим: никаких оценок, советов и интерпретаций от тебя» (буквально в каждом из 13 промптов)
- `raymers`: «Не подменяете рассуждение студента своими выводами», «Не выставляйте баллы, проценты, уровни — только качественную обратную связь»
- `legalmentor_bot`: «НЕ выставляй числовых оценок и баллов» — визуальная шкала блоков (█/░) вместо процентов
- `gb_edu_bot`: «Ты НЕ оцениваешь студента и НЕ выносишь вердикт — это задача преподавателя» (TEACHER_VERIFY)
- `cognitive_interview`: «Не давай правовых заключений... Не навязывай ИИ-решение там, где нужен регламент, человек или база знаний»

**Важное исключение — справочные боты без педагогического запрета:** `alekseev` (прямо отвечает на юридические вопросы от лица персоны, поощряет прямые ответы) и `strategic_transcripts` (чисто справочный Q&A-бот) не содержат этого запрета вообще — потому что их роль другая: не наставник, а эксперт/источник.

**Частичное исключение — `tamozhennik`**: запрет действует только в справочном навыке `reference`, но в обучающих/тестовых навыках (`learning_xrays`, `learning_tstk`, `testing`) LLM прямо инструктируется выносить вердикт (`"correct": true/false`) — то есть режим оценки зависит от типа навыка внутри одного бота, не является сквозным правилом.

### 1.9. Rate limiting и concurrency — идентичный примитив

Без исключений: `user_active_requests: dict[user_id -> int]`, `max_requests_per_user` (почти всегда `= 2`), increment/decrement в try/finally, отказ с сообщением «У вас уже есть активные запросы» при превышении. Не distributed, сбрасывается при рестарте, защищает не от DDoS, а от гонки состояний одного пользователя.

### 1.10. Параллельные реализации Telegram/VK — дублирование, не абстракция

В 10+ ботах одна и та же бизнес-логика продублирована дважды: `bot.py` (Telegram, `telebot.async_telebot`, ручной long-polling `get_updates`) и `bot_vk.py` (VK, `vkbottle.bot`, `BotLabeler`). Отличия только в транспортном слое (получение user info, typing-индикатор, разбивка сообщений по лимиту платформы — 4000 vs 4096 символов), но `ChatMemory`, роутинг, state machine скопированы почти дословно в оба файла. Явно прокомментированная в коде особенность vkbottle («vkbottle calls ALL matching handlers») потребовала отдельного guard-механизма (`_has_dedicated_handler`), которого нет в Telegram-версии — асимметрия платформ, требующая ручной синхронизации логики при каждом изменении.

### 1.11. Механизм «фаз» / дозирования поддержки — реализован по-разному, не унифицирован

В отличие от предыдущих пунктов, этот паттерн **не имеет единой реализации** — каждый бот изобретает его заново своим способом:

- `gb_analytical_bot`: явная двухфазная state machine на dict'ах (`user_in_review_dialogue`, `user_awaiting_revision`), команда `/revision` переключает фазу.
- `cognitive_interview`, `reflector`, `reflector_kolb`: линейная последовательность фаз/слоёв с обязательным confirmation gate между ними, продвижение по флагу `layer_complete` в JSON-ответе LLM.
- `cicero_bot`/`corruption`, `legalmentor_bot`: не состояние бота, а внутренняя (не показываемая студенту) диагностика уровня внутри одного промпта — 3–4 уровня («Начальный/Развивающийся/Сформированный» или «Уровень 1–4»), определяемые LLM заново на каждом ходу по истории диалога, без сохранения в state.
- `raymers`: глубина ответа управляется не автоматически, а по явному запросу пользователя (`REWRITE_SIMPLER`/`REWRITE_DEEPER` и т.п.) — не прогрессия, а меню.
- `tamozhennik`: адаптивная эскалация подсказок внутри одной сессии теста (при ошибке — подсказка с вариантами), не межсессионная фаза.
- `alekseev`, `strategic_transcripts`, `dialogic_supportive_bot`, `dialogic_argumentative_bot`: фаз нет вообще — единый режим для всех запросов.

### 1.12. Версионирование/сравнение работы пользователя — три разных реализации одной идеи

- **Явный счётчик итераций в коде** (`gb_analytical_bot`): `user_review_iteration`, `user_revision_previous_text` — единственный бот, где это структурные данные, а не только промпт-инструкция.
- **Через LLM + окно истории диалога** (`cicero_bot`/`corruption` editor-навык, `legalmentor_bot` debate replay): версия не хранится структурированно — LLM сравнивает текущий текст с предыдущим, беря его из `conversation_history` (ограничено последними N сообщениями) или из персистентной SQLite-истории сессии.
- **Coherence-check между этапами одной сессии** (`reflector`, `reflector_kolb`): не сравнение версий во времени, а проверка логической связности между уже пройденными слоями текущей сессии (`layer_complete: false`, если данные противоречат друг другу).

### 1.13. Инфраструктурные паттерны без содержательной вариации

Встречаются в подавляющем большинстве ботов в идентичном виде:
- Разбивка длинных ответов на чанки под лимит платформы (4000 Telegram / 4096 VK).
- Typing-индикатор через фоновую asyncio-задачу (`_typing_loop`, VK `messages.set_activity` каждые 4 сек).
- Retry с экспоненциальным backoff на отправку сообщений (обычно 3 попытки).
- `try/except Exception` вокруг всего пайплайна обработки сообщения с fallback-текстом пользователю и `logger.error(..., exc_info=True)`.
- Отдельная обработка `asyncio.TimeoutError` на этапах классификации интента и генерации ответа с разными пользовательскими сообщениями.
- SSL-контекст вручную через `certifi` (monkey-patch `aiohttp.TCPConnector` в некоторых VK-ботах).
- Конфигурация через `.env` + `python-dotenv`, `PROJECT_ROOT` через `dirname(dirname(abspath(__file__)))`.

## Часть 2. Связь общих паттернов с SC-каталогом (Портфель 42)

Формат идентичен «Словарь соответствий SC-ТЗ.md»: язык SC (абстрактный контракт) ↔ как он реально выглядит в этих 15 ботах.

### SC01 — Dialogue Policy Engine

**Язык SC.** Типы вопроса, hint ladder, reveal rules, first-attempt requirement, эскалация.

**Как выглядит в 15 ботах.** Это и есть паттерн 1.2 (intent classification) — но важно: SC01 у Портфеля 42 шире, чем просто роутинг. Ни в одном из 15 ботов нет отдельного модуля именно «политики диалога» — есть только классификатор *какой навык вызвать*, а собственно deny-паттерны (что нельзя говорить) зашиты не в роутере, а в каждом промпте навыка отдельно (см. SC06 ниже). То есть SC01 в реальности расщеплён на два разных места кода, которые в каталоге считаются одной ответственностью.

**Разрыв.** Классификатор интентов копируется как целый блок промпта (few-shot с «ПРИЗНАКАМИ») в каждый бот заново, с редактированием под новый домен — 13 почти идентичных по структуре, но текстуально независимых копий.

### SC06 — Anti-Solver / Support Dose Controller

**Язык SC.** Управляет, что боту разрешено показать до/после попытки студента; deny paths.

**Как выглядит в 15 ботах.** Это паттерн 1.8 — deny-формулировки в промптах. Самый последовательно повторяющийся SC-компонент из всего каталога: 13 из 15 ботов содержат прямой аналог. Формулировки почти взаимозаменяемы между доменами (педагогика/право/философия/таможня), что подтверждает: это не доменное знание, а единая «философия фреймворка» — сократовский метод вместо прямого ответа.

**Разрыв.** Нигде не реализовано как структура данных (`SupportPolicy` с уровнями и версией) — везде это текстовый список запретов внутри system-prompt, продублированный почти дословно 13 раз с косметическими правками под домен.

### SC07 — Attempt + Revision Lineage

**Язык SC.** Сохраняет попытку как неизменяемый артефакт, строит цепочку версий.

**Как выглядит в 15 ботах.** Паттерн 1.12. Реализовано в структуре данных только в одном боте (`gb_analytical_bot`); в остальных, где версионирование вообще есть (`cicero_bot`, `legalmentor_bot`), это не отдельный артефакт с `parent_id`, а неявное сравнение через LLM, читающий ограниченное окно `conversation_history`.

**Разрыв.** Ни в одном из 15 ботов нет персистентного (переживающего рестарт) хранилища попыток — везде либо in-memory dict, либо (в лучшем случае) SQLite-запись диалога, из которой версия «вычленяется» заново каждым LLM-вызовом, а не читается как структурированное поле.

### SC08 — Rubric / Rater Service

**Язык SC.** Версионирует критерии оценки, таксономию ошибок, механизм разногласий.

**Как выглядит в 15 ботах.** Каждый бот, где есть оценивание (`gb_analytical_bot`, `cicero_bot`, `legalmentor_bot`, `tamozhennik` в обучающих навыках), возвращает свою JSON-структуру с полями таксономии (`errors`, `has_thesis`, `evidence_types`, уровни 1–4 и т.п.) — все разные, ни одна не переиспользуется между ботами.

**Разрыв.** Нет общего `CriterionPackage`. Даже внутри одного бота (`raymers`: `analytical_support` vs `reflection` vs `diagnostic`) три навыка возвращают структурно несовместимые JSON-схемы оценки.

### SC12 — Experiment Orchestrator

**Язык SC.** Разделяет «назначенное условие» и «фактическое воздействие».

**Как выглядит в 15 ботах.** Отсутствует полностью и без исключений. Ни один из 15 ботов не участвует в контролируемом эксперименте (A/B, control group) — все они прямые production-инструменты, не исследовательская инфраструктура.

### SC13 — Version Registry

**Язык SC.** Версии модели/промпта/корпуса с эффективными интервалами.

**Как выглядит в 15 ботах.** Отсутствует полностью. Ни в одном боте нет версионирования промпта или отслеживания, какая версия LLM/корпуса действовала во время конкретного диалога — `usage_tracker` пишет `model` (имя модели), но не версию промпта.

### SC14 — Human Decision Service

**Язык SC.** Переход «машинный кандидат → значимый статус» — явное решение человека.

**Как выглядит в 15 ботах.** Явно реализовано в справочных/верификационных навыках: `gb_analytical_bot::teacher_verification`, `gb_edu_bot::TEACHER_VERIFY`, `hanskelsen_bot::REFERENCE_VERIFICATION` (единственный из 15 ботов с password-gated ролевой моделью — `TEACHER_PASSWORD` из `.env`, единственный явный механизм различения ролей на уровне доступа, не эвристики).

**Разрыв.** Во всех остальных 14 ботах роль пользователя (студент vs преподаватель) определяется эвристически LLM-классификатором по тексту сообщения, а не структурно (см. SC16 ниже) — `hanskelsen_bot` здесь исключение, а не правило.

### SC16 — Identity / Access

**Язык SC.** Доступ на уровне project/course/cohort/role.

**Как выглядит в 15 ботах.** Практически не реализовано. Единственное исключение — `hanskelsen_bot::REFERENCE_VERIFICATION` (пароль из env). Во всех остальных ботах, включая те, где в промптах упоминается роль «преподаватель» (`gb_analytical_bot`, `gb_edu_bot`), проверки идентичности нет вообще — это чистая уязвимость: пользователь, написавший «как преподаватель, проверяю...», пройдёт классификатор.

### SC20 — Benchmark Registry

**Язык SC.** Capability-specific тесты, gold/actual, критический fail блокирует релиз.

**Как выглядит в 15 ботах.** Отсутствует полностью как runtime-механизм. Нигде нет автоматических regression-тестов на промпт. Ближайший артефакт — файл `app/test.py` в некоторых ботах (`gb_analytical_bot`, `alekseev`), но по факту это утилита ручной инспекции векторной БД (`python test.py`, интерактивный вывод в консоль), а не набор fixture с ожидаемым/наблюдаемым состоянием.

### SC04/SC05 — Corpus/RAG + Evidence Graph

**Язык SC.** Реестр источников с полномочиями; связь claim↔evidence с состоянием SUPPORTED/CONFLICTING/UNKNOWN.

**Как выглядит в 15 ботах.** RAG-слой (1.5) реализован сильно и единообразно на уровне «извлечь релевантный фрагмент», но **entailment-проверка** (действительно ли фрагмент поддерживает утверждение, а не просто тематически близок) нигде не реализована как отдельный шаг — это делегировано целиком промпту («НИКОГДА не выдумывай источник, если его нет в контексте» — есть везде, но проверка соответствия смысла, а не только наличия, полагается на добросовестность модели).

## Часть 3. Что не имеет SC-эквивалента (инфраструктурный слой)

Эта закономерность уже отмечалась для `gb_analytical_bot` отдельно и полностью подтверждается на всех 15 ботах: SC-каталог Портфеля 42 описывает исключительно педагогически/эпистемически значимый слой и полностью молчит про инженерную платформу, на которой он работает. Конкретно для всех 15 ботов это:

1. **Двухпровайдерный LLM-слой с защитным парсингом** (1.7) — `model_loading.py`, поллинг Coze/302.ai, `extract_response_text` с regex-фолбэками. Это самый объёмный переиспользуемый некод-специфичный модуль во всём корпусе.
2. **usage_tracker / cost accounting** (1.6) — подсчёт токенов, рублёвая стоимость, JSON vs JSONL хранение. Частично пересекается с SC-духом («аналитика для преподавателя»), но сам механизм — чисто finops-инфраструктура, не про студента.
3. **RAG ingestion pipeline** — `pdfplumber` + `RecursiveCharacterTextSplitter`, метаданные chunk — технический слой под SC04/SC05, но сам чанкинг/индексация нигде в SC-каталоге не описана как ответственность.
4. **Rate limiting / concurrency guard** (1.9) — защита процесса от гонки состояний одного пользователя; ближе всего к SC18 (Teacher Triage), но SC18 — про очередь к человеку-проверяющему, а это — про очередь к самому вычислительному процессу.
5. **Транспортный слой мессенджера** (1.10) — Telegram/VK API специфика, разбивка сообщений, typing-индикатор, SSL. Полностью вне SC-каталога, который абстрагируется от канала доставки.
6. **Retry/timeout/error-handling дисциплина** — универсальный defensive-programming слой, не связанный с доменом.

**Практический вывод для фреймворка**, дополняющий уже сделанный вывод по `gb_analytical_bot`: ядро из пяти SC-модулей подтверждается на всех 15 ботах — каждый из них угадан интуицией разработчика в разной степени полноты, но ни разу не вынесен в переиспользуемую библиотеку:

1. **Dialogue Policy Engine (SC01 + SC06)** — не два отдельных модуля, а один с двумя внутренними частями: (а) intent-классификация — «какой навык уместен сейчас» (паттерн 1.2), и (б) deny/dose-политика — «что этому навыку нельзя говорить» (паттерн 1.8). В коде они физически разнесены (роутер в `bot.py`, запреты внутри каждого промпта `skills.py`), но это разнесение — артефакт копипаста, а не архитектурное решение: в каталоге Портфеля 42 это одна ответственность, и объединять их стоит и во фреймворке.
2. **Attempt Store (SC07)** — персистентная история попыток/версий.
3. **Rubric/Taxonomy Store (SC08)** — единая структура критериев и меток ошибок.
4. **RAG/Evidence Layer (SC04+SC05)** — корпус + проверка, что источник действительно подтверждает вывод, а не просто рядом лежит.
5. **Human Authority Gate (SC14+SC16)** — явное решение человека поверх машинного кандидата, основанное на структурной роли, а не на эвристике LLM. Важная оговорка: SC16 в этих 15 ботах реализован почти нигде (1 случай из 15 — см. выше), но по данным реестра SC01-SC20 имеет статус `deep 3/3` — подтверждён независимо во всех трёх глубоких инженерных разборах всего корпуса 42 ТЗ, наравне с core-компонентами SC07/SC08/SC12/SC14/SC20, с 9 документированными потребителями. То есть это не гипотетический кандидат «на будущее», а компонент с подтверждённым высоким спросом по всему портфелю, который в проанализированных 15 ботах пока реализован эвристически (LLM угадывает роль по тексту) или не реализован вовсе — разрыв между спросом и текущей практикой здесь самый большой среди всех пяти модулей ядра, и именно поэтому его стоит закладывать в фреймворк с самого начала, а не достраивать по факту накопленной боли.

Шестой слой — Platform Adapter (LLM providers + usage tracking + messenger transport + RAG ingestion) — не имеет SC-эквивалента вообще (см. выше), но количественно занимает *больше* кода, чем весь SC-специфичный слой вместе взятый, и должен быть отдельным, наиболее приоритетным к унификации модулем фреймворка, поскольку именно здесь сосредоточен максимальный объём дословно копируемого (и местами багованного — read-modify-write в usage_tracker, гонки в rate limiting) кода.
