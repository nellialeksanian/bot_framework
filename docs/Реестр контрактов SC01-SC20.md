# Реестр контрактов Портфеля 42

Технический разбор всех 20 общих компонентов (SHARED_COMPONENTS SC01–SC20), извлечённых из 42 технических заданий на ИИ-боты.

**Источники:**
- «Исполнимый контрактный субстрат» v1.3 FROZEN (`00_CANON/ИСПОЛНИМЫЙ КОНТРАКТНЫЙ СУБСТРАТ...docx`) — формальные схемы DS/SM/ATF, история их ремонта по проходам P008–P020
- «Shared Component Ledger» v1.4 FROZEN (`00_CANON/SHARED COMPONENT LEDGER...docx`) — определения SC, цитаты требований REQ-XXX/INV-RXX, deny paths
- «Портфоль ИИ-экспериментов ТюмГУ» v2.2 FROZEN (`00_CANON/ПОРТФОЛЬ ИИ-ЭКСПЕРИМЕНТОВ ТЮМГУ...docx`) — архитектурная карта: разделы 2–5 дают человеческое обоснование («почему»), 42 проекта, 8 «созвездий» кластеров, 10 сквозных инвариантов
- `PORTFOLIO MAP + MACHINE GRAPH v2.0 FROZEN.xlsx` — листы `SHARED_COMPONENTS`, `PROJECT_COMPONENTS`, `COMPONENT_COUNTS`, `COMPONENT_CONTRACTS`, `REQUIREMENT_OVERLAP`, `SCHEMA_TRACE`, `CONTRACT_SCHEMAS`, `STATE_MACHINES`, `ACCEPTANCE_FAMILIES`, `GRAPH_EDGES`

Ни один компонент не является работающим сервисом: везде `LIVE_PILOT_AUTHORIZED=NO`. Реализован только research-валидатор для ветки delegated-authority (SC14) и benchmark-протоколов (SC20).

**Как читать:** SC — идея/ответственность на человеческом языке. DS (формальная схема) — конкретные поля данных. SM (машина состояний) — в каких состояниях объект бывает и какие переходы разрешены. ATF (тестовое семейство) — приёмочные тесты (позитивные и негативные сценарии), проверяющие контракт. «Почему» — обоснование компонента человеческим языком из архитектурной карты v2.2, с конкретными проектами, на которых оно построено.

**Методологическое примечание.** Раздел 4 карты v2.2 «Двадцать повторяющихся узлов» нумерует их 01–20 в собственной логике — эта нумерация НЕ совпадает с SC-номерами из Ledger, соответствие ниже указано по смыслу для каждого компонента. Также числа потребителей в разных срезах документов (`SHARED_COMPONENTS` vs `PROJECT_COMPONENTS` vs текст Ledger) местами расходятся на ±1 проект — это отражает то, что кодировка портфеля уточнялась по мере проходов P008–P023; расхождения отмечены явно там, где найдены.

## SC01 — Dialogue Policy Engine

**Статус:** demand confirmed, не извлечён · Потребители: 21 проект (наибольший спрос) · Deep-подтверждение: 2 · Кластеры: A_DLG, C_LANG, D_RES, E_ADV

Управляет типом вопроса, лестницей подсказок (hint ladder), правилами раскрытия ответа, требованием первой попытки, дозой поддержки и эскалацией — весь порядок диалоговой помощи в сократическом режиме.

Остаётся локальным для каждого проекта: TargetAction, допустимые типы вопросов, предметные формулировки подсказок.

Формальная схема не извлечена: статус `DEMAND_CONFIRMED__CONTRACT_NOT_YET_EXTRACTED`. Косвенно упомянут как `applies_to` в ATF13 вместе с DS07/SM07/SC06.

> Несколько проектов независимо пришли к одному и тому же экспериментальному вопросу — Dynamic Questioning vs Static Scaffold — это КогниЛингво, Социологический навигатор и «ФинМыш».

### Почему

Соответствует узлу «01. SOCRATIC / REFLECTIVE INTERLOCUTOR» карты v2.2 (раздел 4) и созвездию A — QUESTION/SOCRATIC/METACOGNITIVE (раздел 3): система не должна выдавать решение как конечный продукт, а обязана регулировать последовательность вопросов, требовать оснований и постепенно снимать поддержку. Ключевой аргумент — из раздела 5.1 «Сначала определить человеческое действие»: пока не определена операция, которая должна остаться человеческой, невозможно отличить scaffolding от замещения. Автор карты отдельно фиксирует, что три проекта независимо подошли к одной и той же развилке Dynamic Questioning vs Static Scaffold — «КогниЛингво» (FD42-002), «Социологический навигатор» (FD42-016) и «ФинМыш» (FD42-031) — это и есть основание считать Dialogue Policy общим, а не локальным механизмом.

## SC02 — Simulation / Persona Engine

**Статус:** challenger draft · Потребители: 11 проектов · Источник схемы: FD42-020 «ИИ-Эксплуатант», author-TZ (P013) · Кластер: B_SIM

Держит роль, состояние, цель, границу знания, сценарные события и управляемую вариативность симулируемого «другого» — клиента, пользователя, оппонента, рыночного условия.

**Схема DS08 — SimulationRun + ExecutionObstacle:**
- `SimulationRun`: run_id, attempt_ref, task_ref, simulator_policy_version, literalness_profile_version, persona_profile_version (опц.), timestamps/status
- `ExecutionObstacle`: obstacle_id, run_ref, attempt_ref, step_ref, obstacle_type, evidence_ref, message_ref, `advisory_content_present` (bool — нарушение роли, если true), status

**Состояния SM08:** `DRAFT_RECORDED` → `SIMULATION_STARTED` → `EXECUTION_TRACE` → `OBSTACLE_RECORDED` → `SIMULATION_COMPLETED` → `REVISION_ELIGIBLE` → `RESIMULATION`
Отказные состояния: `INSUFFICIENT_INPUT`, `SIMULATOR_FAILED`, `ROLE_BOUNDARY_VIOLATION`, `CONFIG_DRIFT`

**Таксономия препятствий (требует калибровки):** MISSING_INFORMATION, AMBIGUOUS_INSTRUCTION, UNEXECUTABLE_STEP, CONTRADICTION, ENVIRONMENT_UNKNOWN, OTHER

**Тест ATF15 — literalness + no-advice boundary.** Позитив: draft студента существует → simulation run следует literalness-политике → конкретное препятствие связано с run/attempt/step/evidence. Негатив: совет или переписывание под ролью «буквального пользователя»; симуляция до черновика; препятствие-сирота без привязки. Severity: HIGH.

> «Источник напрямую требует: предшествующий независимый черновик студента; строго буквальное симулированное использование; отчёт о препятствиях на уровне шага; никаких советов и переписывания; повторное тестирование со сравнением версий; анти-делегирование.» — author-TZ FD42-020, substrate v1.3, раздел 18 (P013)

### Почему

Соответствует узлу «02. PROFESSIONAL SIMULATOR» карты (раздел 4) и созвездию B — SIMULATION/PERSONA/MODELED OTHER (раздел 3). Если у SC01 машина создаёт поддержку, то здесь она создаёт сопротивление — удерживает позицию клиента, пользователя, рынка, оппонента. Три опорных проекта дают три разных обоснования одной архитектуры: «Песочница консультанта» (FD42-007) показывает, зачем нужен управляемый, а не свободно болтающий симулятор — «у студента получается богатая беседа, а у исследователя — новый природный объект, который ещё надо поймать»; «ИИ-Эксплуатант» (FD42-020) показывает поведенческий evidence вместо оценочного суждения — «ваша инструкция недостаточно ясна» превращается в «действие не удалось на таком-то шаге»; «Гельминтолог-детектив» (FD42-006) радикализирует семью — Другой становится намеренно ошибающимся источником, и ошибка превращается из дефекта модели в сконструированный учебный объект.

## SC03 — Case / Scenario Generator

**Статус:** challenger draft · Потребители: 9 проектов · Источник схемы: FD42-006 «Гельминтолог-детектив», author-TZ (P012) · Кластер: E_ADV

Генерирует варианты задач, ошибок, датасетов и стресс-событий с явными параметрами сложности и provenance — «уникальный кейс» не значит «невоспроизводимый».

**Схема DS09 — DefectSet + StudentDiagnosis:**
- `DefectSet`: defect_set_id, task_ref, source_standard_ref, generator_policy_version, model_config_version, intended_defect_count, defects[], guard_status
- `StudentDiagnosis`: diagnosis_id, defect_set_ref, actor_ref, found_items[], correction_prompt_ref, created_at

**Таксономия дефектов (provisional):** TIMING, HOST, INFECTION_ROUTE, LOCALIZATION, OTHER. Контролируемый набор из четырёх дефектов (controlled four-defect stimulus) на один сценарий.

**Состояния SM09:** `SOURCE_STANDARD_ACCEPTED` → `DEFECT_SET_GENERATED` → `DEFECT_SET_GUARDED` → `STUDENT_DIAGNOSIS` → `ARGUMENTED_CORRECTION` → `CORRECTION_PROMPT` → `EVALUATION` → `TRANSFER`

**Тест ATF16.** Позитив: валидный four-defect set, связанный с принятым эталоном. Негатив: несовпадение заявленного и фактического числа дефектов; неразмеченный (UNKNOWN) набор показан как валидный; авто-исправление модели сохранено как рассуждение студента. Severity: CRITICAL.

> Важная граница reuse: гейт «первая попытка перед вмешательством» (CP11A) здесь явно неприменим — намеренно неверный стимул по замыслу появляется до попытки студента, а не после.

### Почему

Соответствует узлу «14. SCENARIO / CASE GENERATION» (раздел 4) и частично созвездию E — ERROR/OPPONENT/ADVERSARIAL LEARNING (раздел 3), где Устюгова («Гельминтолог-детектив», FD42-006) задаёт четыре типа контролируемых биологических ошибок и требует не просто найти дефект, но аргументировать коррекцию. Человеческое обоснование: «уникальный кейс» не должен означать «невоспроизводимый» — карта явно противопоставляет живое динамическое возражение заранее подготовленным карточкам альтернатив и персонализированный стресс-сценарий одинаковому сценарию для всех, формулируя это как программу исследования продуктивного сопротивления.

## SC05 — Source + Evidence Graph

**Статус:** не извлечён · Потребители: 15 · Deep-подтверждение: 2 · Кластеры: D_RES, F_FB

Связывает утверждение (claim) с физическим источником, evidence-регионом, состоянием entailment, конфликтом и коррекцией.

Возможные состояния (концептуальные): SUPPORTED, PARTIAL, CONFLICTING, UNKNOWN

> Карта называет этот компонент «возможно одним из самых важных инфраструктурных результатов всей программы»: авторитетно сохранённый текст не превращается автоматически в верный ответ.

Главный аргумент — раздел 5.7 целиком: «authoritatively stored text не превращается в automatically valid answer»; система должна уметь явно сказать «источники расходятся» или «в утверждённом корпусе нет основания». Особая важность — для научной литературы, социологии, гуманитарных дисциплин, права, медицины и истории (перечислено явно в разделе 5.7).

## SC15 — Module Release States

**Статус:** deep 3/3, схема ожидается · Потребители: 5 · Кластеры: H_GOV, F_FB, MULTIMODAL

## SC18 — Teacher Triage + Queue Capacity

**Статус:** не извлечён · Потребители: 3–4 (данные расходятся между срезами) · Кластер: F_FB

Прямо называются источники этого инварианта: FD42-011 («ИИДА») и FD42-023 делают teacher workload частью ценности проекта, а музыкальный Hephaestus (FD42-028) отдельно вводит queue capacity и overload mode.

Видит повторяющиеся механизмы, ошибки, общие компоненты, готовность и негативные результаты across всего портфеля — обслуживает не отдельный проект, а сами отношения между проектами.

> «Если искусственно присвоить SC19 всем 42 проектам, счёт станет большим и бессмысленным» — ноль прямых потребителей называется здесь «хорошим нулём», а не пробелом.

Стратегические решения остаются человеческими: аналитика может показывать паттерны, но не устанавливает приоритеты автоматически.

### Почему

Не входит в перечень 20 узлов раздела 4 как «продукт для проекта» — это единственный компонент, который карта описывает не через consumer-проекты, а через саму программу как целое (раздел 1 «Что изменилось, когда сорок два проекта положили рядом»). Сама карта и есть первый артефакт уровня SC19 — она видит повторяющиеся механизмы, пустоты, кластеры across всего портфеля. Методологическая рамка: «главный эффект карты возникает, когда формальные названия перестают быть единицами сравнения» — сорок два проекта не превращаются в сорок два типа решений; числа членства читаются как рабочие минимумы, а не финальный подсчёт.

### Источники

- Методологическая рамка — карта v2.2, раздел 1 «Что изменилось, когда сорок два проекта положили рядом» и вводный абзац раздела 3 («Числа членства пока следует читать как рабочие минимумы…»)
- Формальный статус — xlsx, `SHARED_COMPONENTS` строка 19 (`GLOBAL_ONLY__NO_DIRECT_PROJECT_CONSUMER`), `COMPONENT_COUNTS` строка SC19
- Прямых текстовых цитат конкретно про SC19 в разделах 3/4/5 карты нет — компонент не выделен как отдельный узел, это артефакт уровня portfolio governance, зафиксированный только в xlsx/Ledger

### Проекты-потребители

Точный список не документирован явно. По `SHARED_COMPONENTS`/`COMPONENT_COUNTS`: 0 прямых потребителей. Однако лист `PROJECT_COMPONENTS` в текущей версии xlsx фиксирует один edge со статусом operations для FD42-011 («ИИДА») в колонке SC19 — то есть в последней версии матрицы это уже не строгий ноль, а n=1. Расхождение между версией, зафиксированной в тексте Ledger (0), и текущим xlsx (1) не устранено в источниках.

## SC20 — Benchmark Registry

**Статус:** core · 3/3 deep + найден исполняемый дефект · Потребители: 18–19 (расхождение между срезами) · Deep: FD42-023, FD42-028, FD42-031 + challenger FD42-034 · Кластер: все технические capability

Делает приёмку качества capability-specific, привязанной к контексту и воспроизводимой — «один приятный пример» не значит «готово к релизу».

**Схема DS05 — BenchmarkPacket (v0.2, после исполняемого ремонта):** benchmark_id/version, capability_ref, context_bounds, config_version, fixtures, `expected_state`, `actual_state` (добавлено при ремонте), gold_authority, severity

**Состояния SM05:** `DRAFT` → `LABELED` → `CALIBRATED` → `PASS_BY_SLICE` / `FAIL_BY_SLICE` → `DRIFTED` → `REVALIDATION_REQUIRED` / `INVALIDATED`

Единственный компонент со задокументированным найденным дефектом спецификации: ранняя версия схемы путала ожидаемое (`expected_state`) и фактически наблюдённое (`actual_state`) — исполняемый валидатор показал, что packet со статусом PASS мог не содержать фактических результатов теста. Дефект исправлен в v0.2.

**Тест ATF09 + ATF18 (persisted trace, 8 сценариев).** ATF18: проверка бандла, детерминированный повтор, обнаружение подмены незапечатанной нагрузки, дрейф версии протокола/манифеста/матрицы полномочий/графа зависимостей. Результат: 8/8 PASS.

**Deny paths:**
- один приятный пример = приёмка
- агрегированный балл скрывает критический провал
- модель пишет собственный gold-эталон
- бенчмарк одного модуля даёт готовность соседнему
- старая валидация автоматически наследуется новой конфигурацией

### Почему

Не выделена отдельным узлом в разделе 4 (это межузловая техническая подложка), но прямо обоснована через раздел «Общая техническая подложка» и множественные deny paths, разобранные в Ledger. Главный аргумент: «"один приятный пример" не значит "готово к релизу"». Связан с идеей раздела 5.6 (authority per workcell: gold labels остаются у domain owner) и с созвездием H, где подчёркивается необходимость reusable Experiment Orchestration Layer — Benchmark Registry выступает его измерительным аналогом для capability readiness, а не для причинных выводов эксперимента.

## Общее методологическое примечание

Часть расхождений в числах потребителей (SC18, SC19, SC20 — ±1 проект) отражает то, что xlsx `PROJECT_COMPONENTS` — самый свежий и структурированный срез данных, тогда как текст Ledger v1.4 писался раньше и не всегда идеально с ним синхронизирован. Разделы 6 и 7 карты v2.2 («Общая техническая подложка» и «Пустые зоны портфеля») цитируются здесь по названию и содержательной близости, но не были вычитаны построчно — если нужна точная дословная цитата с номером абзаца из этих двух разделов (актуально для SC16, SC17, SC19), это отдельный уточняющий проход.
