
Новые тесты покрывают HTTP/SSE/polling, изображения, ошибки/таймауты/cancellation,

используют заглушки API и не расходуют платные запросы.

## Что происходит с хабом

Проверены текстовые и vision-запросы, а также отдельный GET `/models` без ключа.
В диагностике комбинации TLS verify on/off и trust_env on/off дают
`ConnectError → EndOfStream → SSLEOFError` примерно за 5 секунд.
Отключение проверки сертификата, как в старом боте, проблему не устраняет.
HTTP-ответа нет, поэтому это не подтверждённая ошибка ключа, модели или JSON.
Причина на уровне сервера/маршрута/VPN ещё не установлена.

```powershell
uv run --no-sync python scripts/diagnose_hub.py --env ../organizer_bot2/organizer_bot/.env
```

Небезопасный диагностический probe добавляется только явным флагом
`--allow-insecure-probe`; он не меняет конфигурацию приложения и не отправляет ключ.
Не выключайте TLS в рабочей конфигурации ради обхода этой ошибки.

## Как повторить реальные примеры

Из корня репозитория; команда платная и обращается к настоящим моделям:

```powershell
uv run --no-sync python scripts/validate_live_examples.py `
  --env ../organizer_bot2/organizer_bot/.env `
  --organizer ../organizer_bot2/organizer_bot `
  --reflector ../reference_repos/reflector_kolb `
  --customs ../reference_repos/customs_bot
```

После восстановления хаба достаточно повторить заблокированные сценарии:

```powershell
uv run --no-sync python scripts/validate_live_examples.py `
  --env ../organizer_bot2/organizer_bot/.env `
  --organizer ../organizer_bot2/organizer_bot `
  --reflector ../reference_repos/reflector_kolb `
  --customs ../reference_repos/customs_bot `
  --cases hub_qwen_text hub_302_text hub_qwen_image hub_302_image
```

Обвязка импортирует оригинальные функции: у organizer заменён только импорт
инфраструктурного `call_with_fallback`; у customs выделена исходная функция
intent, чтобы не создавать лишние глобальные логгеры/токенизаторы. Отчёты не
содержат ключей, endpoint-адресов или исходных ответов; диагностика предметной
ошибки исходного organizer может создать `artifacts/matrix_failures.jsonl`.
Скрипт не отправляет сообщений пользователям. Любой провал даёт exit code 1.

## Обязательные оставшиеся проверки перед публикацией

1. Получить рабочий доступ к хабу (нужен ли VPN/другой адрес), повторить четыре
   заблокированных случая и проверить Qwen → резерв хаба при недоступности
   только Qwen. Сейчас живьём проверен маршрут отказа всего хаба → прямой 302.ai.
2. Предоставить токены тестовых Telegram/VK-ботов и конкретные разрешённые chat/peer
   IDs. В использованном `.env` оба messenger-токена пусты. Боевые чаты не трогались.
3. В каждой платформе проверить входящий текст и команду без двойного вызова,
   длинный ответ с emoji, кнопки/callback, typing, PNG и DOCX на вход/выход,
   edit/delete и штатную остановку. Убедиться, что журнал содержит правильные
   user/chat/skill IDs и нет потери/дублирования сообщений.
4. Пройти полные пользовательские сценарии последних ботов с владельцем
   предметной логики; отдельно проверить случаи «не таблица», повреждённый JSON,
   истечение дедлайна и недоступность всех резервов.
5. Указать реальные тарифы хаба/302.ai, сверить token usage и оценку стоимости
   с учётом особенностей биллинга провайдера.
6. Только после успешной приёмки подготовить отдельную ветку, проверить diff
   на секреты и исходные данные, затем загрузить изменения и провести review.

Флаги `publication_allowed=false` и `messenger_live_verified=false` в текущих
отчётах отражают этот незавершённый статус, а не автоматическое разрешение на deploy.
